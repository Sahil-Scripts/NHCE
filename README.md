## 📌 Executive Summary & Problem Statement

Global Anti-Money Laundering (AML) and Counter-Terrorism Financing (CFT) compliance is plagued by a catastrophic operational bottleneck:
- **95% to 98% of AML alerts generated by legacy rule engines are False Positives.**
- Legacy systems rely on rigid, static SQL rules (e.g., `SELECT * WHERE amount > 10,00,000`).
- Professional money laundering syndicates easily bypass static thresholds by using:
  1. **Smurfing / Structuring**: Breaking massive illicit sums into batches right under mandatory reporting limits (e.g., ₹1,85,000–₹1,95,000 hovering below the ₹2,00,000 FIU threshold).
  2. **Multi-Hop Circular Routing**: Bouncing funds across 4 to 10 intermediary shell accounts before returning to the beneficiary, creating zero net balance changes.
  3. **High-Velocity Conduit Accounts**: Retaining balances for less than 15 minutes to defeat batch-window surveillance.
  4. **Dormant Account Reactivation**: Hijacking long-abandoned accounts to execute rapid high-value transfers.

**AEGIS** replaces rigid heuristics with an **autonomous, closed-loop probabilistic reasoning engine**. Rather than firing uncontextualized alerts, AEGIS extracts 43 behavioral features, estimates uncertainty using **Shannon Entropy**, strategically gathers optimal graph evidence, performs **Bayesian belief convergence**, and generates an official, audit-grade **FIU-IND Suspicious Transaction Report (STR)** in under 2 seconds.

### 1. Why Shannon Entropy? (What Kind & Why It's Used)

#### What Kind of Entropy?
AEGIS implements **Binary Shannon Information Entropy**:
$$H(p) = -p \log_2(p) - (1 - p) \log_2(1 - p)$$
where $p = P(\text{fraud})$ is the probability of the transaction being illicit.

#### Why Is It Used?
In standard machine learning, classifiers output a probability $p$, but **they have no concept of their own uncertainty**. 
- If $p = 0.50$, the classifier is in maximum state of confusion ($H(0.5) = 1.0\text{ bit}$).
- If $p = 0.98$ or $p = 0.02$, uncertainty is virtually zero ($H \approx 0.14\text{ bits}$).

**The Fundamental Flaw of Legacy Systems:**
Legacy systems treat every trigger identically. If an account hits a rule, it alerts, flooding analysts with low-confidence borderline noise.

**The AEGIS Solution:**
AEGIS treats investigation as an **entropy-minimization game**:
1. When an event first arrives, initial entropy is high ($H \ge 0.20$). The system recognizes: *"I do not know enough to freeze this user's funds."*
2. Rather than escalating to a human, AEGIS autonomously executes investigation loops to gather targeted evidence.
3. Every piece of verified evidence (e.g., discovery of a 3-hop shell ring or ₹1.9L structuring pattern) drives the probability toward $1.0$ (or toward $0.0$ if counter-evidence is found).
4. As $p \to 1.0$, Shannon Entropy drops:
   $$H(0.95) = -0.95 \log_2(0.95) - 0.05 \log_2(0.05) = 0.069 + 0.216 = 0.286$$
   $$H(0.98) = -0.98 \log_2(0.98) - 0.02 \log_2(0.02) = 0.028 + 0.113 = 0.141 < \theta$$
5. **Principled Stopping Rule**: When $H(X) < 0.20$, epistemic uncertainty is mathematically resolved. The system terminates investigation and issues a confident verdict.

### 2. Why XGBoost (Extreme Gradient Boosting)?

#### Why Not Deep Learning or Simple Logistic Regression?
1. **Tabular Domain Dominance**: Financial transaction data is heterogeneous, tabular, and mixed-type (continuous amounts, categorical payment channels, integer frequencies). Gradient Boosted Decision Trees consistently outperform Deep Neural Networks on tabular data without requiring massive parameter counts.
2. **Extreme Class Imbalance Handling**: Financial crime represents $< 0.1\%$ of real transactions. XGBoost allows precise weighting of positive instances (`scale_pos_weight`) and optimizes directly on tree splits that separate high-risk clusters.
3. **Handling Non-Linear Threshold Interactions**: Money laundering patterns rely on compound conditionals (e.g., `Amount in [180k, 199k]` AND `Time_Delta < 300s` AND `Counterparty_Count > 5`). Trees naturally carve these non-linear hyperplanes.
4. **Explainability & Feature Attribution**: XGBoost provides native Gain and Weight importances, enabling the extraction of exact feature drivers (e.g., `structuring_risk: 0.2941`, `in_out_ratio: 0.2215`) for mandatory FIU regulatory audit trails.

#### The 43 Engineered Features
AEGIS extracts 43 features per transaction categorized into 5 families:
- **Velocity Dynamics**: `txn_count_1h`, `txn_count_24h`, `velocity_burst_ratio`, `rolling_mean_gap_sec`.
- **Amount & Limit Ratios**: `amount_ratio_to_avg`, `log_amount`, `threshold_proximity_200k`, `structuring_score`.
- **Flow Symmetry (Conduit Behavior)**: `credit_debit_balance_ratio`, `in_out_turnover_velocity`, `net_retention_rate`.
- **Counterparty Dispersion**: `counterparty_shannon_entropy`, `unique_beneficiaries_24h`, `fan_out_degree`.
- **Historical Account Deviation**: `dormancy_reactivation_gap_days`, `prior_sar_count`, `kyc_risk_tier`.

### 3. Why Adaptive Evidence Planning (Information Gain vs. Cost)?

In a live production banking core with millions of users, querying the core database, running multi-hop graph algorithms across 10 million nodes, or calling external KYC/PEP APIs costs significant latency and computational budget.

AEGIS implements an **Information-Theoretic Evidence Planner**:
$$\text{Utility}(S) = \frac{\mathbb{E}[\Delta H(S)]}{\text{QueryCost}(S)}$$

| Evidence Source | Query Cost (Latency/Compute) | Expected Information Gain $\Delta H$ | Priority Under High Uncertainty |
| :--- | :--- | :--- | :--- |
| **Counterparty Graph Traversal** | Medium ($\approx 12\text{ms}$) | **High (0.45 bits)** | **Highest Utility (Queried 1st)** |
| **Temporal Velocity Analysis** | Low ($\approx 3\text{ms}$) | **High (0.42 bits)** | **High Utility (Queried 2nd)** |
| **Historical Baseline Deviation** | Low ($\approx 2\text{ms}$) | Medium (0.25 bits) | Moderate Utility |
| **External KYC / Sanctions Registry** | High ($\approx 150\text{ms}$) | Low-to-Medium (0.15 bits) | Deferred unless necessary |

The planner prevents wasted computations by greedily choosing the evidence query that eliminates the greatest amount of uncertainty per millisecond spent.

### 4. Why Graph Topology & Directed Network Traversal?

Money laundering is fundamentally a **relational network crime**. An individual transaction examined in isolation almost always looks legitimate (e.g., a standard transfer of ₹1,45,000 via RTGS). The criminal signature only becomes visible when the transaction is viewed as a **directed edge in a financial transaction graph**:
$$G = (V, E)$$
where $V$ represents accounts (nodes) and $E$ represents transactions (directed weighted edges).

AEGIS uses **NetworkX** and custom recursive **Depth-First Search (DFS)** algorithms to detect:
1. **Circular Layering Rings**:
   $$A \xrightarrow{\text{RTGS}} B \xrightarrow{\text{NEFT}} C \xrightarrow{\text{IMPS}} D \xrightarrow{\text{UPI}} A$$
   Funds cycle through multiple legal entities and return to the originator with small percentage fees subtracted, disguising the illegal origin.
2. **Conduit / Pass-Through Behavior**:
   Accounts with a high transit velocity:
   $$\text{Conduit Score} = 1 - \frac{|\text{Total Inflow} - \text{Total Outflow}|}{\text{Total Inflow} + \text{Total Outflow}}$$
   A score near $1.0$ indicates that the account is merely a transit pipe retaining no funds.
3. **Smurfing Fan-In / Fan-Out**:
   Dozens of disparate retail accounts transferring ₹1.9L into a central aggregator within 3 hours.

### 5. Why Bayesian Belief Convergence?

When evidence is gathered from completely different domains (e.g., an XGBoost statistical score, a graph cycle finding, and a timestamp velocity spike), legacy systems combine them using arbitrary, hand-tuned heuristic point sums (e.g., `points += 20`). This breaks down in production.

AEGIS uses **Bayesian Likelihood Ratio (LR) Updating**:
$$\text{Odds}_{\text{posterior}} = \text{Odds}_{\text{prior}} \times \prod_{i=1}^{N} \text{LR}(e_i)$$
where the Likelihood Ratio for evidence $e_i$ is:
$$\text{LR}(e_i) = \frac{P(e_i \mid \text{Fraud})}{P(e_i \mid \text{Legitimate})}$$

- **Cycle Detected in Graph**: $\text{LR} = 8.5$ (Multiplies suspicion odds by 8.5x).
- **Structuring Pattern Identified**: $\text{LR} = 6.2$.
- **Long-term Dormancy Reactivation**: $\text{LR} = 4.1$.
- **High In-Out Turnover (>95%)**: $\text{LR} = 3.8$.
- **Verified Clean Counterparty / Salary Source**: $\text{LR} = 0.15$ (Divides suspicion, moving probability toward legitimate).

The odds are converted back to a bounded probability:
$$P(\text{fraud} \mid E) = \frac{\text{Odds}_{\text{posterior}}}{1 + \text{Odds}_{\text{posterior}}}$$

This guarantees mathematical consistency, eliminating arbitrary threshold bugs.

## 🔬 Step-by-Step Architecture: Stages A through E

### Stage A: Multi-Dimensional Risk Normalization
- **File**: [`backend/core/scorer.py`](file:///s:/NHCE/backend/core/scorer.py), [`backend/core/features.py`](file:///s:/NHCE/backend/core/features.py)
- **Input**: Raw transaction row + historical context DataFrame.
- **Process**:
  1. Computes 43 behavioral features.
  2. Passes feature vector through pre-trained XGBoost model (`xgb_model.pkl`).
  3. Applies sigmoid normalization to map raw margin to prior $P_0(\text{fraud}) \in [0.0, 1.0]$.
- **Output**: Initial risk prior $P_0$ and top 4 feature importance drivers.

### Stage B: Entropy Confidence Estimation
- **File**: [`backend/core/entropy.py`](file:///s:/NHCE/backend/core/entropy.py)
- **Input**: Current belief state $p$.
- **Process**:
  1. Computes Shannon Entropy: $H(p) = -p \log_2(p) - (1-p) \log_2(1-p)$.
  2. Compares against threshold $\theta = 0.20\text{ bits}$.
- **Decision**:
  - If $H(p) < \theta$: System is confident. Bypass Stages C & D and jump to Stage E.
  - If $H(p) \ge \theta$: System is uncertain. Trigger Stage C for adaptive evidence collection.

### Stage C: Adaptive Evidence Planning
- **File**: [`backend/core/planner.py`](file:///s:/NHCE/backend/core/planner.py)
- **Input**: Current entropy state, catalog of available evidence sources.
- **Process**:
  1. Evaluates each available sensor (Counterparty Graph, Temporal Velocity, Account History, KYC Registry).
  2. Computes utility score: $\text{Utility} = \Delta H / \text{Cost}$.
  3. Dispatches query requests in order of descending utility.

### Stage D: Graph Traversal & Temporal Pattern Matching
- **File**: [`backend/core/graph_engine.py`](file:///s:/NHCE/backend/core/graph_engine.py), [`backend/core/temporal.py`](file:///s:/NHCE/backend/core/temporal.py)
- **Input**: Target account ID, transaction graph $G$, timestamp sequence.
- **Process**:
  1. **Cycle Detection**: Executes bounded DFS to detect directed cycles ($k$-hop rings from length 3 to 12).
  2. **Conduit Traversal**: Traces inflow-to-outflow time latency.
  3. **Structuring Search**: Scans for bursts of deposits between ₹1,80,000 and ₹1,99,999.
  4. **Velocity Burst**: Detects $\ge 5$ transactions occurring within a rolling 60-minute window.
  5. **Dormancy Reactivation**: Identifies accounts inactive for $> 90\text{ days}$ suddenly transacting $\ge ₹1,00,000$.

### Stage E: Bayesian Belief Convergence & Decision
- **File**: [`backend/core/bayesian.py`](file:///s:/NHCE/backend/core/bayesian.py), [`backend/core/decision.py`](file:///s:/NHCE/backend/core/decision.py)
- **Input**: Prior $P_0$, observed evidence set $E$.
- **Process**:
  1. Successively updates probability distribution using Likelihood Ratios: $P_0 \to P_1 \to P_2 \dots \to P_{\text{converged}}$.
  2. Re-computes final Shannon Entropy $H_{\text{final}}$.
  3. Evaluates decision boundary:
     - If $P_{\text{converged}} \ge 0.75$: **ACTION: BLOCK**.
     - If $P_{\text{converged}} < 0.75$: **ACTION: APPROVE**.
  4. Formats full forensic dossier and generates FIU-IND compliant STR audit JSON.

## 🚀 Installation, Setup & Quickstart

### Prerequisites
- **Python 3.10 or higher**
- **Node.js 18.0 or higher** (with npm)
- **Git**

### 1. Clone the Repository
```bash
git clone https://github.com/Sahil-Scripts/NHCE.git
cd NHCE
```

### 2. Set Up Python Backend
```bash
# Create virtual environment (optional but recommended)
python -m venv venv
# Activate on Windows:
venv\Scripts\activate
# Activate on Linux/macOS:
source venv/bin/activate

# Install dependencies:
pip install -r backend/requirements.txt
```

### 3. Verify Backend Engine
```bash
# Train the model and verify synthetic datasets:
python backend/train.py

# Run backend diagnostics:
python backend/run_diagnostics.py --stage all
```

### 4. Set Up Frontend Web Application
```bash
cd frontend/frontend
npm install
```

### 5. Launch the Complete System
You can launch both the frontend and backend using the unified startup scripts:

**On Windows (One-Click Launch):**
```cmd
# Double click or execute:
start_all.bat
```
*(Or navigate to `frontend/frontend` and run `npm run dev`)*

The dashboard will be live at:
👉 **`http://localhost:8080/`**
